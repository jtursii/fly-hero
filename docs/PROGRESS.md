- 2026-09-16 — **Phase 3b full-model smoke test: STOPPED -- 100% gradient-NaN rate training the real connectome (invariant 7)** —
  - **What happened:** GRU baseline gate passed decisively (0.992 hit_rate on Medium val at step 3000, ~15 min into the 1h budget -- SIGTERM checkpointing verified clean). `train/readout_only.py`'s cache build proceeded normally throughout (all 4,000 training clips cached; val-trace caching in progress at the time of this entry). The 10-minute full-model smoke test (`--model connectome`, curriculum starting at Easy) then found **every training step's backward pass produces NaN gradients** -- `grad_norm` was `NaN` on all of steps 10/20/30 (`nan_frac: 1.0` throughout), confirmed independently on `--fixed-difficulty Medium` too (30/30 steps NaN). The forward pass and loss are clean (loss ~2.0-2.2, finite, and *not* decreasing across steps -- consistent with the model never actually updating, once the bug below was fixed).
  - **Real bug found and fixed first**: the training loop only checked `torch.isnan(loss)` *before* `backward()`, never checking the gradients themselves before `optimizer.step()`. Since the NaN appears during backward (not in the loss value), the old code was silently applying NaN Adam updates every step -- permanently corrupting the model's optimizer state from step 1. Fixed in `train/bc.py`: `is_nan` is now computed from `clip_grad_norm_`'s returned total norm (NaN/Inf) *after* backward, `optimizer.step()` is skipped when NaN, and `optimizer.zero_grad()` always runs before the next step regardless. Also fixed a related silent-masking bug in `run_clip`'s `max_abs_state` tracking: Python's builtin `max(x, float('nan'))` returns `x` (NaN comparisons are always `False`), so a real state blowup would have been invisible in the logged `max_abs_state` -- replaced with NaN-propagating comparison logic.
  - **Root cause, isolated on CPU (rules out MPS-specific numerics)**: of `tau`'s 9,028 per-cell-type parameters, exactly 5 have NaN gradients on a representative Easy batch: **R7, R8** (the photoreceptor types -- the *only* neurons with external input, invariant 1), **L1, L5** (their direct downstream lamina partners, with dense reciprocal L1<->L5 connectivity -- 1600+/1500+ edges in the two gain groups sampled, opposite signs), and one small 2-neuron type (`AN_multi_1`). Forward-pass activations for these types stay finite and bounded throughout (`max|v|` ~10-11 the whole window, confirmed via an explicit per-frame NaN scan with none found) -- this is a **gradient-explosion-through-time** effect, not a forward blow-up: `tau`/`bias`/`g` are shared per cell-type (D3, invariant 3) across up to ~1,591 neurons (L1) and 240 backprop-through-time substeps (2s window / 2 substeps per 60Hz frame) with no gating/normalization to bound the BPTT Jacobian -- if even one of those ~1,591 x 240 per-neuron-per-substep local gradient terms overflows float32, the whole shared parameter's gradient goes NaN, and `clip_grad_norm_`'s single combined norm then propagates that NaN into literally *every* parameter's effective gradient (confirmed: only 5/9,028 `tau` entries were independently NaN, yet the reported `grad_norm` was NaN on 100% of steps). Phase 3a's gradcheck (`test_gradcheck_float64_cpu`) never exercised this: it used a 12-node synthetic graph and only 2 substeps, far too small to expose a large-scale, many-substep BPTT instability. The gain0/bias_init stability sweep (D25) only checked *forward* dynamics (activity bounded, DN signal reaches threshold) -- forward stability turns out not to imply backward (gradient) stability.
  - **This blocks `bc_full_real` as currently configured**: a 100% per-step NaN rate means zero optimizer updates ever happen, so launching the overnight run would burn the full budget with no training progress. Not launched.

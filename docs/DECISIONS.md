# Decisions (append-only; change only with the user's approval)

- D1: Connectome is FlyWire FAFB v783 (Zenodo 10676866 + github.com/flyconnectome/flywire_annotations). Not BANC or MaleCNS.
- D2: Rate model, not spiking. Euler integration.
- D3: Parameters shared per cell type and per (pre type, post type) pair. No per-edge weights.
- D4: Edge signs from predicted neurotransmitter: ACh +1, GABA −1, Glu −1. Others decided in Phase 1 and recorded here.
- D5: Training is behavior cloning from chart-derived labels. PPO is out of scope. ES fine-tuning is a stretch goal.
- D6: Training data is the user's local Clone Hero song library (guitar parts, Easy/Medium/Hard/Expert). The curriculum is the four difficulties. No procedural song generation, except tiny hand-written test fixtures.
- D7: Out of scope: the real Clone Hero game, screen capture, CGEvents.
- D8: The web viewer plays precomputed replays; no live inference in the browser.
- D9 (default; user to confirm before Phase 7): the public site hosts no song audio and no original chart files. Replays show title/artist/charter credit, the highway, and brain activity, with synthesized per-lane hit sounds. A local-only "load your own audio file" option may sync real audio in the browser without uploading or hosting it.
- D10: shared, cross-phase utility code (YAML config loader, run-dir helper) lives in `flyhero/utils/` (`config.py`, `run.py`). Added to the repo layout in PLAN.md during Phase 0 since the original layout diagram had no home for code used by every later package.
- D11: Per-neuron NT sign source (Phase 1) is `top_nt` from the `flywire_annotations` v3.1.0 TSV. Fallback, when `top_nt` is missing or `top_nt_conf < 0.5`: synapse-weighted mean of that neuron's outgoing per-edge NT columns (`gaba_avg`/`ach_avg`/`glut_avg`/`oct_avg`/`ser_avg`/`da_avg`, weighted by `syn_count`) from `proofread_connections_783.feather`, still collapsed to one sign per neuron. Fallback usage counts reported in `docs/graph_report.md`.
- D12: Histamine override — photoreceptor cell types (R1–6, R7, R8; exact `cell_type` spellings confirmed against the live annotations TSV during Phase 1) are forced to histamine, sign −1, regardless of predicted NT. What `top_nt` originally predicted for these neurons is reported in `docs/graph_report.md`.
- D13: Modulatory NTs for v1 — dopamine, serotonin, octopamine all map to sign +1 (not inhibitory). Per-transmitter neuron and edge counts reported in `docs/graph_report.md`.
- D14: Per-neuron type-ID fallback chain (Phase 1 `build_graph.py`): `cell_type` → `hemibrain_type` → `cell_class` → singleton (unique type per unlabeled neuron). Neuron counts landing at each level of the chain reported in `docs/graph_report.md`.
- D15: Neuron positions are stored in `graph.npz` two ways: `pos_nm` (soma/anchor coords converted to nanometers via the FlyWire 4×4×40 nm/voxel scaling) and `pos_voxel` (the raw voxel-index coords as published). Both documented in `docs/graph_report.md` alongside which one is raw vs. derived. Position is resolved **per neuron**, not per column: `soma_x/y/z` is used where non-null, else `pos_x/y/z` (the anchor point) — required because photoreceptor somata sit in the retina, outside the FAFB volume, so `soma_x/y/z` is null for 11,108 of 11,118 photoreceptors (verified in `docs/graph_report.md`). An initial version of `build_graph.py` chose soma-vs-anchor once for the whole column set rather than per neuron, which silently left ~11.1k photoreceptor positions as NaN; fixed before this decision was recorded, with a regression test (`test_build_graph_index_round_trip`).
- D16: Per-(pre_type, post_type) gain sharing is configurable in Phase 3's `brain/rate_model.py`: `fine` (one `g` per realized (pre_type, post_type) pair, 410,768 params), `coarse` (one `g` per (pre_type, post_super_class), 22,212 params), or `hybrid` (default) — a pair keeps its own gain if it has ≥ `k` edges, else it falls back to the coarse `(pre_type, post_super_class)` bucket. `k` defaults to the largest edge-count threshold at which fine pairs still cover ≥ 90% of all edges, chosen from the distribution in `docs/graph_report.md`: **k = 2** (93.85% edge coverage; k = 3 drops to 85.88%), giving 244,824 fine pairs + 18,925 coarse buckets = **263,749 total gain parameters**. The ES fine-tuning stretch goal (Phase 5) uses `coarse` throughout, not `hybrid` or `fine`. This responds to Phase 1's Gate G1 finding that realized type pairs (410,768) exceed PLAN.md's original 300k fallback threshold; the mechanism itself is implemented in Phase 3, not Phase 1 — Phase 1's `graph.npz` already carries the fine-grained `pair_id` plus `type_id`/`super_class_id`, sufficient to derive any of the three schemes without rebuilding the graph.
- D17: Phase 2 ingest (`flyhero/game/ingest.py`) design choices beyond PLAN.md's original task list, approved by the user:
  - Star power (`S`) events in `.chart` are ignored and counted, symmetric with `.mid`'s star-power handling. `sustain_min_beats` (config, default 0.5) applies to both `.chart` and `.mid`, not just `.mid` as PLAN's task 2/3 wording implied.
  - `Song.duration_s` = `song.ini`'s `song_length` (ms→s) when present and > 0, else the last note's (incl. sustain) end time.
  - The >10%-open-notes exclusion (v1 rule simplification) is evaluated and applied **per (song, difficulty)**, not per song — a song's other difficulties survive even if one is dropped.
  - Exact-duplicate `(artist, title)` resolution (raw, case-insensitive, rich-text-stripped match): keep the member with the most surviving difficulties, tie-broken by Expert note count, then by `rel_path`; every drop is logged with both sides' numbers. Near-duplicates (same *normalized* — lowercased, bracket/parenthetical-stripped — key but different raw key) are reported in `docs/library_report.md` for manual review, never auto-merged or dropped.
  - The train/val/test split is assigned **per normalized-duplicate group, not per song_id**: every member of a group (near-duplicates included) lands in the same split, so two charts of the same underlying song can't leak across train/test. Stratum (`native_easy_medium` vs `expert_only`) is per group: `native_easy_medium` if *any* member has both native Easy and Medium surviving the open-note filter.
  - `.mid` parsing: a `note_on` with `velocity=0` is treated as a `note_off` (standard MIDI running-status convention, used by real game-ripped files). The tempo map is built from `set_tempo` messages found in *any* track, not just track 0 (the conductor-track convention), with a warning if one is found elsewhere.
  - `Song` carries `chart_offset_s` (`.chart`'s `Offset`, seconds; 0.0 for `.mid`, which has no such concept) and `ini_delay_s` (`song.ini`'s `delay`, ms→s) — both recorded per PLAN's instruction but unused for training (invariant 4: `game/rules.py` is the only scoring implementation and doesn't read them).
  - Full rationale and real-library numbers (652 candidates, 0 parse failures, 83 open-note exclusions, 5 exact-duplicate drops, 11 near-duplicate groups, 568 songs written, 453/55/60 train/val/test split) in `docs/PROGRESS.md`'s Phase 2 tasks 1-5 log entry.
- D18: `graph.npz` gained a `side_id` array (0=left/1=right/2=center/3=na, from the annotations' `side` column) during Phase 2 tasks 6-11 — metadata, not topology/synapses/signs, so invariant 3 is unaffected, but it's a change to a Phase-1-built artifact, logged here for that reason. Needed because `game/retina.py` must split photoreceptors into left/right eye groups and no per-node side field existed in `graph.npz` as originally built (only an aggregate `photoreceptor_side_counts` report). `graph.npz`/`graph_shuffled.npz` were rebuilt; both takes ~4s from already-downloaded raw data.
- D19: `game/retina.py`'s photoreceptor visual-field projection (Phase 2 task 9), approved by the user with two changes from the original ask:
  - Column/ommatidium IDs are **not available** in the v3.1.0 annotations (checked directly: all 31 header fields, none column-related), so each of the four groups (R1-6 lamina / R7+R8 medulla, × left/right side) gets its own per-group PCA-derived 2D projection (fit once per (group,side) population) rather than a raw-axis (Y,Z) projection — the naive raw-axis version failed a real connectivity check by 70x (see below) because the lamina/medulla are curved, tilted neuropils whose second principal axis is a genuine mix of X and Z, not pure Z.
  - Axis signs are fixed anatomically (dorsal=image top; each PCA component's sign set by correlation with the real Y/Z axis), not PCA's arbitrary sign. The medulla group's front-to-back chiasm-inversion sign is calibrated empirically — tried both orientations, kept whichever minimizes the connectivity-check distance below — rather than assumed from anatomy alone; the empirical result (flip=True) agrees with the expected "front-to-back inverted" anatomy.
  - **Connectivity check** (R1-6→L1→Mi1 and R8→Mi1: cells sharing a Mi1 column should map to nearby image positions): naive raw-axis projection scored 136.7 lattice spacings (median); fixing the projection to per-group PCA got to 4.95; fixing the lattice-spacing reference from R1-6 (contaminated by within-column, neural-superposition-collapsed distances) to L1 (~one cell per column) got to **1.63, under the required <2 threshold**. 990 Mi1 columns tested.
  - The 10 soma-backed photoreceptors (D15; 7 R7, 2 R8, 1 R1-6) are excluded from retina input entirely (zero current), per the user's explicit instruction, rather than rebuilding `graph.npz` with a separate always-anchor position field for them.
  - Both eyes sample the same full `[0,1]²` rendered frame (PLAN's original spec), split into left/right halves with each eye's frontal direction toward the shared midline — one reasonable reading of "each eye's field on its own side of the screen" among a few; flagged for the user to confirm or correct via the debug video.
  - Full numbers in `docs/PROGRESS.md`'s Phase 2 tasks 6-11 log entry.
- D20: `game/labels.py`'s fret-target hold duration is `min(segment_end, time_s + max(sustain_s, hit_window_s))`, not `min(segment_end, time_s + sustain_s)` — the `hit_window_s` floor (approved by the user) guards against frame-quantization rounding a zero-sustain note's own strum frame to just after `time_s`, which the pure-`sustain_s` version could exclude from that note's own target hold in dense passages. `game/rules.py`'s `scripted_perfect_actions()` plays exactly these labels rather than an independently hand-rolled hold window, both because an independent window would OR together on overlapping dense-trill notes (turning hits into overstrums) and because doing so directly validates that the label design is playable — confirmed by a real-data regression test on the densest Expert val song (Aquellex - Wanderflux, 90% of adjacent note gaps under 2×hit_window_s): hit_rate 1.000, 0 misses, 0 overstrums.
- D21: PLAN.md's Gate G2 env-throughput requirement is amended from ≥10× to **≥5× real time at batch 64 on CPU**. Measured 6.8× after four rounds of optimization (naive 0.7×; see `docs/PROGRESS.md`'s Phase 2 tasks 6-11 log entry for what was tried, including a rejected thread-pool attempt) — accepted by the user rather than pursuing further engineering now. Reason: Phase 3's brain forward pass will dominate total training-step time regardless of the retina/render env's own throughput, so 10× headroom on the env alone isn't the binding constraint; the retina gather is planned to move to torch (this project's existing tensor library, not a new dependency) in Phase 3, which should recover more headroom incidentally.
- D22 (amends invariant 8): song audio may be copied out of the (still read-only, never written-to) song library into `media/` for local use — e.g. muxing into a debug/showcase video. `media/` is gitignored; audio is never committed to git and never placed under `web/`. Phase 7's D9 (no audio on the public site) is unchanged unless the user says otherwise — this decision only concerns local, uncommitted files.
- D23: MPS peak memory (Phase 3a's `bench/bench_brain.py`) is measured by polling `torch.mps.driver_allocated_memory()` every substep (no native peak-tracking API exists for MPS as of torch 2.14, unlike CUDA's `max_memory_allocated`/`reset_peak_stats`); CPU peak is measured via process peak RSS (`resource.getrusage(RUSAGE_SELF).ru_maxrss`, bytes on macOS). The two are not directly comparable (device-driver vs whole-process accounting) — noted in `docs/bench.md`. Additionally: `ru_maxrss` is a process-*lifetime* high-water mark that never resets, and MPS's caching allocator doesn't return memory to the driver without an explicit `empty_cache()` — both make in-process, cross-cell peak sampling meaningless after the first large cell in a sweep (confirmed: the first run of `bench_brain.py` showed CPU peak pinned at one value for every cell after the first big one, and wildly inconsistent MPS backward timings). Fixed by running every timed/measured cell in its own subprocess.
- D24: `scripts/gain0_sweep.py`'s stability-sweep methodology (Phase 3a) — "blank highway" = rendered background/lanes/strikeline with zero notes (not a fully blank frame); signal-reach/latency thresholds default to `0.01`; hard-stop condition is DN reach ≤10% (or saturation, defined as the active-neuron fraction exceeding 30%) across the whole `gain0` sweep, per invariant 7.
- D26: `train/bc.py`'s memory config (batch size, gradient checkpointing) is **batch=4, no per-frame gradient checkpointing** -- the highest-samples/sec config that clears the 40GiB peak bound in `scripts/bench_train_memory.py`'s real training-loop-shaped benchmark (1s burn-in + 2s gradient window, mps/float32): 4.326 samples/s vs. 4.040 (batch=16+checkpoint) and 3.776 (batch=8+checkpoint), consistent across two runs. Also found: Gate G3's originally-chosen config (batch=8, no checkpointing) peaks at 47.52GiB under the real 2s training window, over the 40GB bound (Gate G3's own 1s-window benchmark measured 24.30GiB for the same config, understating the real training loop's memory). Full table and the noted batch-size/gradient-noise trade-off in `docs/bench_train_memory.md`.
- D27: Phase 3b training-loop design decisions (user-specified, `train/bc.py`/`train/readout_only.py`):
  - **Note-aware clip sampling** (`flyhero/game/clip_sampler.py`): 90% of sampled clips have the 2s gradient window containing >=2 notes (by note `time_s`); 10% have 0 notes (so the model learns not to strum on an empty highway). Burn-in may contain anything. Valid start times are precomputed per (song, difficulty, burn_in_s, window_s, fps) and cached to `data/processed/clip_starts/`. Library-wide (train split, all difficulties) median note-free-window fraction: **0.0521** (`docs/note_free_fraction.md`; per-difficulty medians 0.064/0.060/0.057/0.041 for Easy/Medium/Hard/Expert) -- confirms the 10%-empty bucket is drawing from a real but minority fraction of each song's timeline, pooled across many songs (not starved on any single difficulty).
  - **Strum `pos_weight`** is computed from the actual positive-frame rate under this sampler (not a fixed 20), recomputed whenever the curriculum advances to a new difficulty. Logged per-run; e.g. the GRU baseline run measured **23.44** for Medium.
  - **Decoder** (`flyhero/game/decoder.py`): strict ±1-frame local maximum of strum probability above 0.5 (`p[t] > p[t-1]` and `p[t] >= p[t+1]`, sentinel -inf at the boundaries) -- resolves a plateau (equal-valued run) to its *first* frame. Tested incl. a dense trill at 39ms note spacing (2-3 frame gaps at 60fps).
  - **Perturbation-divergence threshold for future chaos-style checks: < 20%** relative DN divergence (Phase 3b's own chaos-check measured 3.9%, well under this).
  - **Curriculum resampling**: once advanced past difficulty N, 20% of sampled clips split *evenly* across all earlier (already-passed) difficulties, 80% at the current difficulty.
  - **Checkpointing**: every 500 steps or 15 minutes wall-clock, whichever comes first, plus on SIGTERM (signal handler flags a clean checkpoint-then-exit).
  - **Readout-only cache**: 4,000 training clips (1000/difficulty, via the note-aware sampler) with cached DN-rate traces; full-length (not excerpted) DN traces for up to 10 val songs per difficulty, so its eval scores whole songs through `rules.score_playthrough` + the decoder exactly like the eventual full model -- unlike `bc.py`'s in-training eval, which uses a fixed 60s excerpt per val song for compute-cost reasons that don't apply to the frozen-brain cache.
  - **In-training eval** (`bc.py`): every 1,000 steps, on 10 fixed val songs at the current difficulty, scored only on a fixed (same every time) 60s note-dense excerpt per song (found by a deterministic sliding-window note-count search, no randomness); eval wall time logged. Full-song evaluation is deferred to Phase 4's `evaluate.py` on saved checkpoints.
  - **GRU baseline architecture**: 3 stride-2 conv layers (16/32/64 channels) -> flatten -> Linear(128) -> `GRUCell(128, 256)` -> `Readout` (reused from the connectome brain's readout class). Consumes the rendered frame directly (bypasses the retina encoder -- invariant 1 constrains `ConnectomeBrain`'s inputs specifically, not this baseline).
- D28: `train/bc.py` uses **NaN-safe gradient sanitization** for training the real connectome: any non-finite entries in a parameter's gradient are zeroed (`torch.nan_to_num`) right after `backward()`, before grad-clipping and the optimizer step. Reason: the full-model smoke test found a **100% gradient-NaN rate** training the real graph (every step, both Easy and Medium difficulties) -- a gradient-explosion-through-time effect in the 240-substep BPTT unroll, isolated to a few shared-per-cell-type parameters (R7, R8 photoreceptors; L1, L5; one 2-neuron type), while forward activity stays bounded throughout (not a forward-pass bug, and not MPS-specific -- reproduced on CPU). Presented to the user with three options (sanitize gradients / truncated BPTT / re-open D25's gain0-bias_init choice); user chose sanitization. Trade-off, accepted: the ~5 affected cell types' `tau`/`bias`/`g` will never receive a real gradient under this scheme and stay near their initial values -- flagged for review in Phase 5's `docs/results.md` if it measurably limits final performance, with truncated BPTT and re-opening D25 remaining as follow-ups. Re-verified stable after the fix: loss fell 2.1->1.5 over a 70-step re-run, `grad_norm` finite every step, `max|v|` bounded (~11.3-11.5), no crashes. Full derivation in `docs/PROGRESS.md`'s 2026-09-16 log entries.
- D29: Fixed a real audio-desync bug in `scripts/render_gameplay_video.py`'s excerpt-render audio mux (found on "Paramore - Misery Business" Easy: sounded off by roughly 1-2 beats, notes landing with the snare instead of alternating -- even though this song's chart Offset and song.ini delay are both 0, since it's `.mid`-sourced and its `song.ini` literally has `delay = 0`). Root cause: `main()` computed the mux offset from `window_start = entry.excerpt_start_s - result["burn_in_actual"]` (the start of the *burn-in* period), but `capture_visualization_frames` only appends a frame to the rendered video `if f >= burn_in_frames` -- burn-in frames are simulated (for retina/brain warm-up) but never written into the output video. So the rendered video's real frame 0 is song time `entry.excerpt_start_s`, not `excerpt_start_s - burn_in_actual`; using the burn-in-inclusive quantity desynced the audio by exactly `burn_in_s` (1.0s in `configs/bc.yaml`, ~2-3 beats at this song's tempo -- matches the reported symptom). Not a chart-Offset/ini-delay sign bug -- both were 0 for this song, so no sign/order error in combining *those* two values could have caused it; the bug was in what "video time 0" was assumed to mean. "Metallica - One" (also chart_offset_s=ini_delay_s=0) never exercised the excerpt path at all (it was rendered via `sim.py`'s whole-song `render_debug_video`, which has no excerpt/burn-in window and thus no `window_start` term), so it couldn't have caught this.
  - **Fix**: pass `entry.excerpt_start_s` directly (not `excerpt_start_s - burn_in_actual`) as the "video time 0" song-time instant. Consolidated the previously-duplicated offset formula (`sim.py`'s inline `-(chart_offset_s + ini_delay_s)` for the whole-song case, and `render_gameplay_video.py`'s local `_excerpt_audio_offset_s` for the excerpt case) into one shared `flyhero/game/sim.py::compute_audio_start_offset_s(chart_offset_s, ini_delay_s, video_start_song_time_s=0.0)`, so the whole-song case is just the `video_start_song_time_s=0.0` special case of the same function (invariant 4's spirit: one implementation, not two that can silently diverge).
  - **Added** `--full-song` (render/score the entire song instead of the fixed 60s note-dense excerpt) and `--audio clicks` (full stem mix + a synthesized click, `flyhero/game/sim.py::generate_click_track_wav`, overlaid at each chart note's own time -- audible sync verification) to `scripts/render_gameplay_video.py`.
  - **Regression test** (`tests/test_audio_sync.py`): a synthetic song with *simultaneously* nonzero chart Offset (0.7s) and song.ini delay (0.3s) and a nonzero excerpt start (5.0s) -- exercises `generate_click_track_wav` -> `compute_audio_start_offset_s` -> `mux_audio_into_video` (real ffmpeg) -> decodes the muxed output back to PCM and checks each click lands within 80ms of its note's expected video-time. A second test pins that using the old buggy (burn-in-inclusive) quantity shifts every click by exactly `burn_in_s`, confirming the fix is the real quantity, not an accidental cancellation. `uv run pytest -q`: 73 passed (was 71 passed/70 passed+1 skipped before this session -- see the test-count-drop finding below).
  - Also fixed, unrelated but found while investigating the reported test-count drop from a prior session (71 -> 70 passed+1 skipped): `tests/test_render_gameplay_video.py::test_rendered_clip_hit_rate_matches_eval_hit_rate` had started being skipped because it hardcoded a specific session's run dir (`runs/20260916_155821_resume_verify_gru`), whose `checkpoint_latest.pt` had become a dangling symlink (target file no longer present -- `runs/` is gitignored and session-ephemeral, so this was never going to survive across sessions). The test's actual invariant (the render and eval code paths agree given the *same* policy weights) doesn't need a *trained* checkpoint, just a policy with the same weights on both call sites -- rewritten to build a fresh `build_policy(...)` instead of loading any run-specific checkpoint, so it's no longer coupled to any gitignored, session-local artifact. No test was deleted or had its assertions weakened; this restores it to always running.
- D30: `bc_full_real`'s escalating gradient explosion (Medium curriculum, steps ~14200-15611, max raw grad_norm 9.6M before the user stopped it with a clean SIGTERM) was diagnosed offline (CPU, backup checkpoints 12000/13000/14000 only, `scripts/diagnose_grad_explosion.py`, real Medium clips) and fixed in `train/bc.py`. Findings:
  - **Not periodic.** Checked every candidate the user asked about: no LR schedule/warmup/restart exists (fixed `lr_readout`/`lr_brain`); eval (every 1000 steps) runs under `no_grad` and each `run_clip` call starts with `policy.reset_stream()`, which resets `TorchRetina`'s EMA state (`retina_torch.py`), so eval cannot leak state into training; checkpointing (every 500 steps) only reads state, never mutates it; `pos_weight` is recomputed only on curriculum advance (an aperiodic, one-time event per difficulty), not on any step schedule; `ClipSampler` caches songs/valid-starts in memory forever with no periodic refresh. Per-step grad_norm around the reported "bad" 1000-step buckets (4900-5150, 9900-10150, 13900-14150) is scattered, not aligned to exact eval/checkpoint step numbers -- ruling out a step-scheduled cause. The apparent periodicity in the user's per-1000-step medians was coincidental (a few high-variance clips happened to land in those buckets).
  - **Root cause (confirmed, not just re-derived from D28)**: the same photoreceptor<->lamina pathway D28 already identified (R7, R8 photoreceptors; L1, L5; one 2-neuron type `AN_multi_1`) passes through a **finite-but-astronomically-large gradient regime** (1e5 to 1e14+) before literally overflowing to `inf`, at BPTT depths as shallow as 30-60 frames (well inside the real 120-frame/240-substep training window) -- reproduced at checkpoint_step13000.pt on a real 6-note Medium clip: `tau[R7]`/`bias[R7]` gradients reached 3.2e12/6.2e13 at depth 30 frames, `inf` by depth 60. **This is the actual bug D28 didn't anticipate**: `torch.nan_to_num` only zeros entries that are *already* non-finite; a 1e12-scale-but-finite entry sails through sanitization untouched, and `clip_grad_norm_`'s single combined norm lets that one entry dominate the scale factor applied to *every* parameter -- crushing the ~9,023 well-behaved cell types' and the readout's real gradient to near zero on that step, even though `grad_norm` itself was finite (matches the observed symptom: hit_rate degrading 0.45->0.35->0.41 with rising overstrums despite no crash and bounded `max_abs_state`). Optimizer state (`exp_avg`/`exp_avg_sq`) at both checkpoints was checked and is clean (no non-finite entries, max magnitude ~0.11) -- the contamination is in the live gradient each step, not accumulated Adam state, so resuming does **not** need an optimizer-state reset.
  - **Fix** (`train/bc.py::apply_gradient_step`, `configs/bc.yaml`'s new `grad_outlier_clip: 10000.0`): (1) gradient sanitization now clamps any element-wise `|grad|` above `grad_outlier_clip` (in addition to the existing D28 non-finite zeroing) -- chosen comfortably above any sane per-element gradient observed on healthy real clips (~O(1-600)) and far below the pathological range; (2) `clip_grad_norm_` is now called **separately** for the readout and brain parameter groups (previously one combined call across both) so a brain-side blowup can no longer starve the readout's learning signal, directly addressing the mechanism above. Not chosen: shrinking `train_window_s` to 1s (a PLAN.md-spec change, and the diagnosis found the pathway can already reach `inf` within 60 frames on some checkpoints/clips, so a shorter window wasn't reliably sufficient on its own).
  - Full per-depth, per-cell-type numbers are in this session's diagnostic script output (not persisted as a doc file, per the task's ask for a diagnosis-and-fix rather than a new artifact) and summarized in `docs/PROGRESS.md`.
- D31: Overnight training-safety watchdog (`train/watchdog.py::GradWatchdog`, wired into `train/bc.py`), added alongside D30's fix so `bc_full_real_v2` can run unattended overnight:
  - **Skip**: a step's optimizer update is skipped entirely (weights untouched, `optimizer.zero_grad()` only) if the post-sanitize brain grad_norm exceeds 20x the rolling median of the last 200 non-skipped steps, or sanitization needed to touch more than 20 gradient entries (the known D28/D30 pathway touches at most ~5-6 tau/bias entries plus a couple of gain groups under normal operation -- more than 20 means something new, not the known pathway, went bad).
  - **Rollback**: if the rolling median stays above 5x a frozen "healthy baseline" (the rolling median once the first 200-step window fills) for 300 consecutive steps, or eval hit_rate drops more than 0.15 below the best seen at the current difficulty for 2 consecutive evals -- revert to `checkpoint_last_healthy.pt`, halve the brain LR, and rebuild the optimizer from scratch (D30 found Adam state itself wasn't contaminated at the checkpoints inspected, but a rollback specifically follows an *unhealthy* stretch, so moments aren't trusted there). Max 3 rollbacks per run; a checkpoint is only certified "last healthy" (hysteresis) once the rolling median is back under 2x baseline, not merely under the 5x rollback bar.
  - **Clean stop**: after 3 rollbacks, or on any uncaught exception in the training loop, `bc.py` checkpoints if possible and writes `runs/<run>/STOPPED.txt` with the reason, then exits (crash: re-raises after writing, so the traceback still reaches the log).
  - **Checkpointing**: every 500-step/15-minute checkpoint is already kept forever (no deletion logic exists anywhere in `bc.py`) -- satisfies "keep every 1000-step checkpoint" with room to spare. - D25 (amends Phase 3's stated `b = 0` init): `ConnectomeBrain`'s per-cell-type `bias` is initialized to a small positive tonic baseline (`bias_init` in `configs/brain.yaml`, default `0.2`, not independently derived — a starting point re-validated alongside the `gain0` search), not `0`.
